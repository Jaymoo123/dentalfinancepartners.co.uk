## 3. Blocking the S5 builders

1. **T2 cannot run as specified.** The shared builder is missing four fields every hand-rolled
   builder already emits, so "replace the hand-rolled builders, every existing field survives" would
   regress `sameAs`, `address`, `legalName` and `parentOrganization` on four sites. Fix #2 first,
   as one shared change with a before/after JSON diff, then port.
2. **T2's `sameAs` needs a decision.** The spec says list the 15 brand sites plus the parent. No site
   does this today and no list exists in shared config. `ashfieldtrading.co.uk` was NXDOMAIN at the
   baseline (section 2), so `parentOrganization` would point at a URL that does not resolve.
   Cross-linking 15 lead-gen brands as one entity is also a visible claim about the estate.
   Owner decision, not a builder decision.
3. **T3's "derived from data, not hand-kept" has no machinery.** Every `llms.txt` is a static file;
   the only writer in the repo is the new-site scaffold. Either a generator gets built (a day, not
   an hour) or T3 becomes "hand-edit five files consistently". Recommend the second for now.
4. **T3 must be claims-gated.** Four of the five llms.txt files call the site an accountancy
   practice. Under `ESTATE_CLAIMS_INTEGRITY` that is a Phase 0 item, and it should be fixed before
   the files are enriched, not alongside.
5. **B0 is already built.** The canonical fix is committed (`bb297ab2`) and verified in source on
   all five. Any agent briefed to "fix the canonical bug" will find nothing to do. What is
   outstanding is the deploy, which is owner-triggered.
6. **B3's site list is wrong for charities.** charities blog posts do render a lead form
   (`charities/web/src/app/blog/[category]/[slug]/page.tsx:247,281,302`), landed in `c810c3ff`.
   Re-verify the other six before scoping that wave.
7. **Not checked here:** rendered HTML. Everything above is source. The Opus visual reviewer in the
   S5 plan should confirm FAQ accordion content survives into server HTML (charities already guards
   this explicitly at `page.tsx:104-112`; Medical's kit `FaqSection` is Radix and may not) and that
   the `@id` de-duplication actually resolves where two nodes share one id.
